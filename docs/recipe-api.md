# 레시피 API: 식품안전나라 본문 + 농식품 시간·난이도

## 데이터 역할

- **식품안전나라 COOKRCP01**: 레시피 ID·이름·사진·재료 원문·조리 과정/이미지·조리법·종류·열량·영양 정보. 검색과 상세 화면의 본문은 이 데이터만 사용한다.
- **농식품 포털 레시피 기본정보** (`Grid_20150827000000000226_1`): 매칭된 요리의 조리시간(`COOKING_TIME`)과 난이도(`LEVEL_NM`)만 보완한다. 레시피 ID는 매칭 근거용 metadata에만 기록한다. 농식품의 재료·과정 API는 호출하지 않는다.
- 농식품 연결/인증 오류가 있어도 본문 검색은 계속하며, 시간·난이도는 기본 추정 규칙을 사용한다. 식품안전나라 실패는 검색 오류로 표시한다.

## 설정

`.env.local`의 기존 값을 유지하고 아래 두 항목을 설정한다. 키 값은 클라이언트·로그·테스트 출력에 포함하지 않는다. `.env.example`은 수정하지 않는다.

```env
FOOD_SAFETY_API_KEY=
FOOD_API_KEY=
```

`FOOD_SAFETY_API_KEY`는 COOKRCP01을 승인받은 식품안전나라 키이며 검색에 필수다. `FOOD_API_KEY`는 농식품 기본정보 키이며 보완용이다. 이전 `FOOD_API_INGREDIENTS_KEY` / `FOOD_API_STEPS_KEY` 설정은 사용하지 않는다. 변경 후 `pnpm dev`를 다시 시작한다.

## 매칭

양쪽 이름에서 공백·문장부호를 제거하고 계란/달걀, 쇠고기/소고기를 통일한 뒤 **고유하게 일치하는 요리명**만 매칭한다. 제목이 비슷하거나 중복 이름이 있는 레시피에는 실제값을 전용하지 않는다. 한 값만 유효하면 그 값만 사용하고 나머지는 추정한다. 난이도는 초보환영→초급, 보통→중급, 어려움→고급으로 표준화한다.

## 시간 추정과 보정

기본 분 수 = `5 + 조리 단계 수 × 2 + 재료 수 + 조리법 가산 시간`.

가산 시간(분): 끓이기 12, 찌기 18, 볶기 8, 굽기 15, 튀기기 15, 기타 5. 재료 수는 원문을 쉼표/줄바꿈으로 나눈 수와 수량·단위 표기의 개수 중 큰 값으로 근사한다. 괄호 안 쉼표는 분리하지 않는다. 원문이 비어 있으면 재료를 추측하지 않으며 그 레시피는 재료 검색에 포함되지 않는다.

동일 조리법의 매칭 실제시간이 3건 이상이면 `실제시간 / 기본 추정시간`의 중앙값을 보정계수로 사용한다. 해당 조리법 표본이 부족하면 전체 매칭 중 3건 이상을 사용하고, 전체도 부족하면 계수 1을 사용한다. 이상치 영향을 줄이기 위해 계수는 0.25~4로 제한한다. 추정값은 5분 단위로 반올림하며 최소 5분이다.

**실제 매칭값을 포함한 모든 시간 표시는 `약 N분`**이다. 목록·상세 변환에서 중복 `약`을 제거한다. 이는 경험적 추정이며 소규모 매칭 자료에 대한 보정이므로 정확도나 요리 완료시간을 보장하지 않는다.

## 난이도 추정과 보정

복잡도 = `단계 수 + 재료 수 × 0.5 + 조리법 가산점`(튀기기 4, 굽기 2, 나머지 0).

기본 기준은 10 이하 초급, 18 이하 중급, 그 이상 고급이다. 매칭된 난이도 자료에서 두 등급 이상이 각각 2건 이상이고 복잡도 중앙값이 등급 순서대로 증가하면 가장 가까운 실제 등급 중앙값을 사용한다. 그룹이 겹치거나 한 등급만 있는 경우에도 실제 라벨 3건 이상이면 기본 등급 중심값(초급 7, 중급 14, 고급 23)과의 차이 중앙값으로 복잡도 기준을 보정한다. 편향 보정은 ±6으로 제한한다. 표본이 부족하면 기본 기준을 유지한다.

`Recipe.metadata`에 `timeSource`/`difficultySource`(`mafra` 또는 `estimated`), `matchedRecipeId`, `calibrationSamples`, `difficultyCalibrationSamples`, `estimateVersion`을 기록한다. 실제 매칭 여부와 경험 규칙 여부를 구분해 추후 매칭/모델 개선에 사용할 수 있다.

## 검색과 화면 연결

`GET /api/recipes?ingredient=대파&ingredient=두부&page=1` → `{ recipes, total, page, pageSize }`.

선택한 모든 재료가 식품안전나라 재료 원문에 포함된 레시피를 검색한다(AND, 부분문자열, 공백 무시, 계란/달걀·쇠고기/소고기 통일). 재료는 1~10개, 각 최대 60자다. 페이지당 20건. `searchRecipes` → `RecipeResults` → 기존 목록·상세 표시 흐름은 유지한다. 상세의 인분은 식품안전나라에서 확인되지 않으면 비워 두며 농식품 값으로 채우지 않는다.

두 데이터셋은 1,000건씩 끝까지 조회하며 최대 10,000건을 처리한다. 동시 검색의 중복 조회를 병합한다. 정상 보완 데이터는 서버에서 12시간 캐시하고 보완 자료가 없으면 5분 후 재시도한다. 식품안전나라 네트워크 요청은 페이지당 15초, 농식품 보완 요청은 전체 8초 제한이다. 키나 키가 포함된 원본 요청 URL을 로그에 남기지 않는다.

정적 `dist/` 호스팅에는 별도 서버/서버리스 `/api/recipes`가 필요하며 필요 시 `VITE_RECIPE_ENDPOINT`로 API 주소를 지정한다.

## 검증

### 재료 원문 정리

`ingredientText.ts`의 공통 로직으로 서버 파싱과 목록 태그·상세 표시에서 같은 이름을 사용한다. 중복/누락 괄호, 줄바꿈, 쉼표 누락으로 이어진 분량을 복구하며 `재료`, `재료 1인분`, `양념장`, `육수` 같은 구분 제목은 재료명에서 제거한다. 실제 재료인 `굴소스`, `다시마육수 100ml`처럼 분량이 바로 오는 이름은 유지한다. 괄호 안 부위·색상·환산량은 삭제하지 않는다. 원본 텍스트는 `rawIngredients`에 보존한다.

`node scripts/audit-recipe-ingredients.mjs`로 전체 공식 DB를 읽기 전용 점검할 수 있다. 괄호 밖 구분자가 이름에 남았거나 복수 분량이 한 항목에 합쳐진 의심 사례를 출력한다. 자동 점검은 자연어 원문의 모든 경우를 보장하지 않으므로 새로운 패턴을 발견하면 회귀 사례를 추가한다.

`pnpm test`: 원문/조리 과정/영양 보존, 고유 이름 매칭, 중복/유사명 제외, 실제값 보완, 표본 기반 보정, 표본 부족 시 기본 규칙, 보완 API 장애, 페이지/캐시/동시 요청, 목록·상세 `약` 표시를 확인한다.

`node scripts/check-hybrid-recipes.mjs`: 설정된 키로 읽기 전용 실조회 후 전체 레시피 수, 보완 레시피 수, 매칭·보정 건수와 소고기 검색 결과 수만 출력한다. 키·원본 URL·응답 원문은 출력하지 않는다.
