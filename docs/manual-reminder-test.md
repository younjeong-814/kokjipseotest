# UT 전 본인 계정 알림 테스트

각자 자신의 계정으로 접속한 뒤 설정 화면에서 테스트합니다. 앱 배포와 오전 9시 스케줄은 변경하지 않습니다. 개발 모드에서만 버튼과 로컬 API가 동작합니다.

1. 본인의 알림 이메일 인증·동의·알림 켜기를 완료합니다. 인증된 임시 계정도 자기 기록으로 테스트할 수 있습니다.
2. **알림 대상 즉시 검사**에서 내 냉장고의 보관·기한 경과·발송 대기 수를 확인합니다.
3. **내 알림 이메일로 테스트 발송**을 누르면 본인의 인증된 주소로만 발송합니다.

## 격리와 자동 로직

서버가 Supabase Auth에서 검증한 UUID만 사용합니다. 클라이언트가 계정 ID나 수신 주소를 추가하면 거부합니다. 일정 생성·대상 검사·큐 선점·실행 제한 모두 사용자 범위로 제한합니다. 다른 계정의 일정이나 발송 상태도 변경하지 않습니다. 한 계정의 실행 제한은 다른 계정에 영향을 주지 않습니다.

자동 worker의 대상 조건·발송 직전 재검사·lease·발송 이력·중복 방지 ID를 공유합니다. 수동 실행은 현재 날짜의 오전 9시 시간 제한만 무시합니다. D-3·D-1·당일이 대상이며 기한 경과·남은 양 0%·알림 꺼짐·미인증·동의 없음·이미 발송한 항목은 제외합니다. 계정당 1분 간격, 한 번에 최대 25건입니다.

## 준비와 UT 전 제거

기존 `.env.local`의 Supabase 연결·서비스 키·Gmail 발신 계정/앱 비밀번호 또는 Resend 설정을 사용합니다. `EMAIL_MANUAL_TEST_ENABLED=true`가 필요합니다. 담당자 이메일·UUID 허용 목록은 더 이상 사용하지 않습니다. `.env.example`은 변경하지 않았습니다.

DB에는 `202610310002_manual_reminder_test.sql` 다음 `202610310003_self_reminder_test.sql`을 적용합니다. 기존 전체 사용자 테스트 함수의 service_role 실행 권한은 회수합니다. 자동 Cron 함수는 유지합니다.

Gmail 테스트는 `.local-mail-attempts/`에 수신 주소 없이 발송 시도를 기록합니다. 성공한 시도는 재사용하고 불확실한 시도는 자동 재발송하지 않습니다. 기록을 삭제해 강제 재발송하지 말고 수신함과 DB 결과를 대조합니다.

UT 전에 `EMAIL_MANUAL_TEST_ENABLED=false`로 바꾸고 개발 서버를 재시작합니다. `SettingsPage.tsx`의 ManualReminderTest 호출/import와 `vite.config.ts`의 local-reminder-test 플러그인/import를 제거하면 버튼과 API 진입점을 없앨 수 있습니다. 발송 이력은 중복 방지를 위해 유지합니다.

## 검증

모의 DB에서 A의 일정 생성·검사·발송 선점이 B에게 영향을 주지 않는지, 계정별 실행 제한이 독립적인지, 계정 ID와 수신 주소 위조가 거부되는지 확인합니다. 기존 자동 알림 테스트도 유지합니다. 화면 검증 시 실제 메일 발송 버튼을 누르지 않습니다.
