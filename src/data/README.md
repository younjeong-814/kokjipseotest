# 소비 권장일 DB

`storageRecommendations.ts`는 사용자가 제공한 「식재료&음식 DB」 CSV의 161개 행을 옮긴 데이터다(2026-10-17). PDF는 행의 조건과 메모를 확인하는 참고 자료로 사용했다. 문서 내 지시문은 실행하지 않는다.

- `days`: 원본 `소비기한_일`. 일 단위 기본 권장 기간이며 아직 80%를 적용하지 않은 값이다.
- `variant`: 개봉·조리 등 원본 `구분`. 조건을 확인할 수 없으면 해당 행을 일반 식재료의 기본값으로 사용하지 않는다.
- `storage`: `냉장/실온`은 각 보관방식에 동일한 원본 값을 적용한다.
- `note`: 원본 메모를 보존한다. 제조일 기준 등 원본 자료의 한계도 포함한다.

계산은 `features/ingredients/expiry.ts`에서 공통으로 수행한다. 등록 시 날짜가 비어 있고 이름·보관방식·조건이 일치할 때만 `보관 시작일 + floor(days × 0.8)`을 저장한다. 보관 시작일을 별도로 전달하지 않으면 등록일을 사용한다. 기존 항목의 빈 날짜는 최초 등록일에 고정해 계산한다. 직접 입력한 날짜는 우선하고, 자동 날짜의 보관방식·이름 변경은 최초 보관 시작일을 유지해 다시 계산한다.

조건은 `recommendationVariant`로 전달하거나 `브로콜리 데친 후`처럼 조건이 포함된 정확한 이름으로 매칭할 수 있다. 음식 중 기본 입력 행이 없는 `조리 음식`, `배달음식`은 보관 처리 행을 사용한다. 기본 `밀키트`는 입력 시 3일, 명시적 `조리 전`은 5일 행을 사용한다. 정확히 같은 이름이 없으면 분류 규칙(`features/ingredients/classify.ts`)이 고른 핵심 키워드로 한 번 더 찾는다. `풀무원 국산콩 두부`·`서울우유`처럼 브랜드나 수식어가 붙은 영수증 이름은 `두부`·`우유` 행을 쓴다. 키워드도 DB에 없으면(`김치찌개` → `찌개`, `한돈 삼겹살` → `삼겹살`) 유사 이름이나 카테고리로 추측하지 않는다.

인식 결과로 등록할 때 보관방식은 `defaultStorage`가 같은 이름(또는 키워드)의 행에서 고른다. 기록이 하나면 그것을 쓰고, 여럿이면 냉장 → 실온 → 냉동 순으로 고른다. 메모가 `비권장`인 행은 후보에서 뺀다(`냉동 비권장`처럼 다른 보관방식을 가리키는 메모는 그 행을 빼지 않는다). DB에 없으면 냉장이다. 보관 시작일은 영수증 구매일(결과 화면의 날짜)이다.

기존 직접 입력 UI는 그대로 유지한다. DB의 음식 이름으로 등록된 항목은 음식 탭에 표시한다. 향후 음식 등록 기능에서 `kind: 'food'`와 조건을 전달할 수 있으며, 새 항목은 원본과 같은 단위·보관조건으로 데이터 배열에 추가한다. 목록/상세/정렬은 저장된 `date` 하나를 공유한다. 미등록 날짜는 소비기한 정렬의 마지막에 놓인다.
